## Findings before backend testing

### P1 — Timestamp convention conflicts with runtime session timezone

apps/api/src/database/v2/runtime.ts:14 configures Sequelize timezone +07:00.
Several repositories write UTC_TIMESTAMP(3) directly into TIMESTAMP columns,
including order-checkout-v2.repository.ts:135,148,159. Other repositories use
CURRENT_TIMESTAMP or Date objects. TIMESTAMP interprets a written wall-clock
value using the session timezone, so UTC_TIMESTAMP written in a +07 session
represents an instant seven hours earlier.

Read-only reproduction on the live server with SET SESSION time_zone='+07:00':
UNIX_TIMESTAMP(CURRENT_TIMESTAMP)-UNIX_TIMESTAMP(UTC_TIMESTAMP)=25200 seconds.
Voucher-claim-v2.repository.ts:52 also compares starts_at/ends_at with
UTC_TIMESTAMP, so a voucher whose dates were written through Date/ORM paths can
be evaluated against the wrong clock. Audit timestamps become inconsistent.

Recommended backend change: use a +00:00 session consistently for API, workers,
migrations and seed; add a regression test using the actual runtime connection
and verify timestamp round-trip, voucher windows and reservation/outbox timing.
Inspect existing transactional data before any corrective timestamp update.

### P1 — Host API configuration points to a different MySQL port

The ignored root .env currently has MYSQL_PORT=3306. Connection using that config
returned ECONNREFUSED. The running project MySQL container publishes 4306→3306;
the same database credentials successfully connect on 4306.

For API/AI running on the Windows host, use the published host port 4306. For
services inside the Compose network, mysql:3306 is correct. Check shell overrides
and deployment mode before changing config. No environment file was edited here.

### P1 — Stock request read contract omits valid database statuses

The design and migration 0005-inventory.ts:35 define pending, approved, rejected,
cancelled and fulfilled. The backend cancel operation updates status to cancelled
and the branch list query returns cancelled rows as well.

apps/web/src/types/inventory.ts:27 only accepts pending/approved/rejected.
StockRequestPage.tsx:207–208 directly dereferences the status lookup without a
fallback. After a pending request is cancelled and the list is refreshed, the
cancelled row can make the page throw while reading statusView.status.

Recommended change: cover all five domain states in the Web DTO and status map,
retain pending-only mutation actions, and test cancel→reload plus fulfilled rows.
The database enum itself is correct and should not be reduced to fit the UI.

## Backend obligations beyond foreign keys

These are approved service/transaction invariants rather than schema drift:

- A branch manager must be active and belong to that branch.
- Order-item variant must belong to the snapshot product.
- Reservation must refer to the correct branch/variant of its order/transfer item.
- A return item and refund payment must belong to the same original order.
- Related chat messages and assistant runs must belong to the same conversation.
- Aggregate payments, refunds, returns and active reservations require locking
  and budget checks; an FK alone does not enforce these sums.
- customer_addresses has no DB-enforced single-default-per-customer constraint;
  any future address write API must preserve that invariant transactionally.
- Category cycle prevention is implemented in the category command repository,
  not by the self-referencing FK alone.

Read-only scans of 12 currently checkable invariants found zero violations.
However, orders/payments/shipments/returns/refunds/stock requests/transfers/chat
are currently empty, so those results do not prove the success paths. Existing
data is mostly seed/catalog: 2 accounts, 1 customer, 1 branch, 6 products,
24 variants, 24 inventories and 24 inventory movements.

Runtime startup gate currently checks table inventory and migration count only;
it does not independently validate FK/CHECK definitions or executed checksums.
The dedicated inspection here found no drift, but future runtime hardening can
make that gate stronger.
